# Git Commit 消息生成器

根据暂存区变更生成 commit 消息并完成质量检查。**严禁在 commit 消息中添加 AI 生成标识或署名。**

## 流程

### 1. 检查与分析

- 运行 `git status`，确认无 merge/rebase/cherry-pick 状态
- 暂存区为空时立即提示；有关键未暂存改动时建议一起提交
- 运行 `git diff --staged`（含 `--stat`），识别模块、文件类型、增删概况
- 检查是否有疑似产物（.env、node_modules、日志、密钥文件等），有则提醒处理
- 初次提交直接建议 `chore: initial commit`
- 混合改动（≥3 个无关模块）须提醒拆分并给出建议

### 2. Review

**每次必查：**
- 敏感信息泄露（密钥、token、密码）— 发现则明确警告并询问是否继续
- 鉴权/权限逻辑漏洞
- 明显的命名问题、缺失错误处理、过度复杂逻辑
- 关键流程缺失测试

**按变更内容触发：**
- 数据库结构/migration → 向后兼容性影响、数据迁移计划
- 批量查询/循环操作 → 性能风险
- 配置格式变更 → 升级注意事项

### 3. 生成 Commit 消息

**Type 选择（优先级从高到低）：**

| type | 场景 |
| --- | --- |
| `feat!` / `fix!` | 破坏性变更（API 签名修改、表结构变更、必需配置项变更、重大依赖升级） |
| `feat` | 新增特性、接口 |
| `fix` | Bug / 安全漏洞修复 |
| `perf` | 性能优化 |
| `refactor` | 代码重构（无行为变化） |
| `test` | 测试代码 |
| `build` / `chore` | 构建与依赖 |
| `ci` | CI 配置 |
| `docs` | 文档 |
| `style` | 格式化、Lint |

**消息规则：**
- **subject**：中文，≤50 字，描述核心影响
- **scope**：仅在能准确指明模块且不冗长时使用
- **body**：说明动机、实现方式、潜在风险；多块用空行分隔
- **footer**：关联 issue；Breaking Change 须加 `BREAKING CHANGE: ...`

### 4. 输出

```
变更统计：<文件数> 个文件，+<新增行> -<删除行>
变更摘要：<一句话核心修改>
受影响模块：<模块列表>
风险评估：<高|中|低> — <理由>
Review 提醒：<发现事项，无则写"无">

Commit 提议：
<type>(<scope>): <subject>

<body>

<footer>

请选择：
1. 使用 — 直接提交
2. 编辑 — 修改消息后提交
3. 取消 — 放弃本次提交
```

等待用户选择后再执行，不要自动提交。
