# Git Commit 消息生成器

请根据 git 暂存区的变更自动生成一个标准的 commit 消息。

## 执行步骤

### 1. 前置检查
- 运行 `git status` 检查仓库状态
- 检查暂存区是否为空（为空则提示用户）
- 检查是否有未暂存的重要变更（建议包含）
- 检查是否处于特殊状态（merge、rebase、cherry-pick等）
- **扫描暂存区是否有不应该提交的文件**（参考后面的.gitignore检查规则）

### 2. 变更分析
- 运行 `git diff --staged --stat` 获取变更统计信息
- 运行 `git diff --staged` 查看具体变更内容
- 分析文件类型和变更模式
- 识别初次提交特殊情况

### 3. 代码Review（根据变更类型针对性检查）
- **安全性**：敏感信息泄露、输入验证、权限控制
- **代码质量**：命名规范、错误处理、代码复杂度
- **性能影响**：算法效率、数据库查询优化（如涉及）
- **测试覆盖**：是否需要补充测试

### 4. 变更分类与优先级判断
- 识别破坏性变更（Breaking Changes）
- 判断主要变更类型
- 评估影响范围和风险等级
- 确定是否需要拆分提交

### 5. 生成Commit消息
- 根据优先级规则选择type
- 生成简洁清晰的subject（限制50个字符以内）
- 补充必要的body说明
- 添加相关的footer信息

## Type选择优先级规则

按以下优先级选择commit类型（当有多种变更时，选择优先级最高的）：

1. **破坏性变更** → `feat!` 或 `fix!` （必须添加!标记）
2. **安全漏洞修复** → `fix`
3. **新API/新功能** → `feat`
4. **Bug修复** → `fix`
5. **性能优化** → `perf`
6. **重构** → `refactor`
7. **测试相关** → `test`
8. **构建系统** → `build`
9. **CI配置** → `ci`
10. **文档更新** → `docs`
11. **代码格式** → `style`
12. **依赖更新** → `chore`

## 破坏性变更识别标准

- **API变更**：接口签名修改、返回值变更、端点删除
- **数据库变更**：表结构修改、字段删除、类型变更
- **配置变更**：配置文件格式修改、必需配置项变更
- **依赖变更**：重大版本升级导致兼容性问题

## 消息格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **type**: 必需，提交类型
- **scope**: 可选，影响范围（如模块名、文件名）
- **subject**: 必需，简短描述（限制50个字符以内）
- **body**: 可选，详细描述变更内容和原因
- **footer**: 可选，关联 issue 或包含破坏性变更说明

## 要求

1. **subject** 使用中文，简洁明了
2. 如果变更较复杂，添加 **body** 部分详细说明
3. 根据实际变更内容智能选择 type，多种变更时选择最主要的类型
4. scope 应该反映受影响的模块或功能
5. 如果有多个不相关的变更，建议拆分提交并提示用户
6. **严格禁止**添加任何AI生成标识（如"Generated with Claude Code"、"Co-Authored-By: Claude"等）
7. commit消息应该简洁、专业、人类可读

## .gitignore 检查规则

### 常见应该忽略的文件/目录
- **系统文件**: `.DS_Store`, `Thumbs.db`, `Desktop.ini`
- **IDE文件**: `.idea/`, `.vscode/`, `*.iml`, `*.swp`
- **日志文件**: `*.log`, `logs/`
- **临时文件**: `tmp/`, `temp/`, `*.tmp`
- **构建输出**: `build/`, `dist/`, `target/`, `node_modules/`, `__pycache__/`
- **环境配置**: `.env`, `.env.local`, `.env.*.local`
- **证书密钥**: `*.jks`, `*.p12`, `*.pem`, `*.key`
- **数据库文件**: `*.db`, `*.sqlite`, `*.sqlite3`

### 检查与处理
1. 运行 `git diff --cached --name-only` 扫描暂存区
2. 识别上述不应该提交的文件
3. 如发现问题文件，提供解决方案：
   ```bash
   # 从暂存区移除
   git reset HEAD <文件路径>

   # 添加到.gitignore
   echo "<文件或目录>" >> .gitignore

   # 删除已提交的文件
   git rm --cached <文件路径>
   ```

- 修改文件数：X个
- 新增行数：+XXX
- 删除行数：-XXX
- 主要变更类型：XXX

### 📋 代码Review总结
- **主要变更**：[概述]（必需）
- **涉及模块**：[列表]（必需）
- **风险评估**：[高/中/低]（必需）
- **发现问题**：[列出需要改进的问题]（如有）
- **改进建议**：[具体的改进建议]（如有）
- **.gitignore检查**：[列出发现的问题文件]（如有）

## 特殊情况处理

### 多功能混合变更与提交拆分
当检测到以下情况时，建议拆分提交：
- 包含3个以上不相关的功能模块
- 同时包含重构和新功能
- 文档变更和代码变更混合
- 配置变更和业务逻辑变更混合
- 包含.gitignore问题的文件需要先处理再提交

**处理方式**：
- 检查变更的关联性
- 强制建议拆分并提供操作步骤

### 破坏性变更
- 自动识别并添加 ! 标记
- 在footer中说明BREAKING CHANGE
- 建议更新相关文档

### 初次提交
- 识别空仓库状态（无历史提交）
- 使用格式：`chore: initial commit` 或 `feat: 项目初始化`

### 敏感代码处理
- 发现可疑代码时，必须在review中明确指出
- 详细说明为什么可疑
- 询问用户是否继续
