# 开发指南

正确性 > 可读性 > 性能。行为不变优先于重构；代码风格服从项目 linter/formatter。

## 工作方式

- 先澄清再编码：假设必须显式说明；多种合理解读并存时，让用户选择。
- 不确定就停下：说明困惑点、可选方案和影响，等待确认，不带着误解继续。
- 发现更简单方案要指出；必要时推回过度设计或风险方案。
- 库、框架、SDK、API、CLI 不确定时，用 context7 或 exa 查最新文档，禁止凭记忆编造。

## 修改原则

- 只做用户要求的事；不增加未要求的功能、抽象、配置或兼容层。
- 只改必须改的代码；匹配既有风格，不顺手重构、格式化或“改进”邻近代码。
- 单次使用的逻辑不抽象；只处理已知可达的失败路径。
- 每一行 diff 都必须能追溯到用户请求；只清理本次改动产生的孤儿 import、变量、函数。
- 发现改动前已存在的死代码或问题，只告知用户，不擅自删除。

## 验证标准

- 把任务转成可验证目标：加校验 → 先写失败测试；修 bug → 先写复现测试；重构 → 前后测试都过。
- 关键业务逻辑必须有测试覆盖；无法描述用例时先澄清需求。
- 重构 legacy 代码前先补测试。
- 多步任务先列简短计划，并标明每步验证点。
- 同一问题尝试 3 次未解决，停止试错，汇报现状、证据和假设，等待指示。

## 正确性底线

- `catch` 必须记录、重抛或转显式返回值，禁止吞错。
- 轮询、重试、爬取必须有显式最大次数变量。
- 资源关闭必须覆盖所有退出路径，包括异常路径。
- 函数签名应暗示副作用；禁止隐式写入可变全局状态。
- 前提条件写成断言或显式校验，而不是注释。
- 涉及钱、权限、用户数据、并发、加密时，主动提示用户审阅。
- 代码优先自解释；关键业务逻辑、公共 API、并发、权限、金额、兼容性相关代码必须用英文注释或文档注释补充 why、业务约束、边界条件和陷阱。
