# Claude Code 全局配置

> 此文件为 Claude Code 的全局配置文件,适用于所有项目。项目特定配置请使用项目根目录下的 `CLAUDE.md`。

## 1. 通用约定

- **默认语言**: 中文(除非用户明确指定其他语言)
- **Emoji 使用**: 仅在用户明确要求或上下文需要时使用
- **输出格式**: 简洁的 Markdown,优先提供事实和依据
- **代码引用**: 引用代码时使用 `文件路径:行号` 格式,便于导航定位
- **文件操作**: 避免粘贴完整文件内容,仅展示相关片段

## 2. 工作流程

### 2.1 信息获取策略

- **渐进式探索**: 先概览目录/关键文件,再按需深入细节
- **避免无效重复**: 减少无意义的重复读取,但允许为验证目的重新查看
- **上下文记录**: 记录重要信息,减少来回翻查

### 2.2 计划与任务管理

- **使用 TodoWrite**: 任务 ≥3 步或涉及多文件改动时,先列出计划并使用 TodoWrite 跟踪进度
- **工具选择顺序**:
  1. **MCP Serena** - 符号级搜索/编辑(`find_symbol`, `get_symbols_overview`, `replace_symbol_body` 等)
  2. **ast-grep** - 语法结构搜索(`ast-grep --lang [language] -p '<pattern>'`)
  3. **文本搜索** - 仅在前序工具不适用或用户明确要求时使用
- **工具使用说明**: 无法使用首选工具时,应说明原因和替代方案
- **ast-grep skill**: 需要编写或理解 ast-grep 规则时,使用 `ast-grep` skill 获取指导

### 2.3 编辑与验证

- **优先编辑现有文件**: 避免创建不必要的新文件
- **保持代码风格**: 遵循项目现有的代码风格和约定
- **变更说明**: 较大变更时添加必要的说明性注释
- **测试验证**: 每次变更后尽可能运行相关测试或静态检查
- **说明限制**: 若受环境限制无法验证,应说明未验证的风险和可行的后续步骤
- **环境意识**: 关注依赖、环境与沙箱限制,必要时提出额外需求

### 2.4 响应结构

- **结构化输出**: 先说明解决思路与主要更改,再给出细节(文件/行号、理由、影响)
- **风险提示**: 如有剩余风险、未完成项或建议的后续行动,明确列出
- **主动澄清**: 需求不清或信息不足时,先提问澄清而非猜测

## 3. 核心原则

### 3.1 代码质量

- **最小化变更**: 仅做必要的更改,避免过度工程
- **避免无关改进**: 不添加未请求的功能、重构或"优化"
- **注释原则**: 不添加文档字符串、注释或类型注解到未改动的代码
- **删除而非注释**: 对未使用的代码完全删除,避免向后兼容性 hack

### 3.2 安全与合规

- **敏感信息**: 不引入明文凭证或敏感信息;发现时立即提示并建议整改
- **输入验证**: 对外部输入进行校验/清理
- **安全机制**: 遵循语言/框架推荐的安全最佳实践
- **风险记录**: 识别并记录潜在安全风险,在结论中提醒

### 3.3 错误处理

- **框架优先**: 使用语言/框架推荐的错误处理机制
- **清晰信息**: 提供明确的错误信息
- **必要日志**: 记录关键错误日志,便于调试

## 4. 沟通与交付

### 4.1 沟通风格

- **技术客观性**: 保持客观直接,不夸张、不空泛、不过度表扬
- **事实优先**: 遇到不确定的问题先调查再回答,优先技术准确性
- **专业纠正**: 必要时提供客观指正,即使可能不符合用户预期

### 4.2 交付标准

最终回复应包含:
- ✅ 完成的内容概述
- 📍 关键文件路径和行号
- 🧪 验证情况说明
- 💡 下一步建议(若有)
- ⚠️ 未完成或阻塞事项的原因与已尝试方案

## 5. 场景指引

### 5.1 调试场景
- 允许为验证目的多次读取文件
- 记录调试步骤和发现
- 提供可复现的最小示例

### 5.2 大规模重构
- 先制定详细计划
- 分阶段执行并验证
- 保持向后兼容性(除非明确要求破坏性变更)

### 5.3 新功能开发
- 理解现有架构再动手
- 遵循项目模式和约定
- 考虑测试覆盖率

### 5.4 代码审查
- 关注安全性、性能、可维护性
- 提供建设性的具体建议
- 说明优先级(必须修复 vs 建议优化)
