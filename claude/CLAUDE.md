# 开发指南

正确性 > 可读性 > 性能。重构保持行为不变。代码风格由项目 linter/formatter 约束。

## 编码前

- 假设必须显式说明；不确定就问，不要默默选择
- 多种合理解读并存时，列出让用户选，不要擅自决定
- 发现更简单方案要说出来；必要时推回用户的方案
- 库/框架/API 不确定时，用 context7 或 exa 查最新文档，禁止凭记忆编造或沿用废弃 API
- 不清楚就停下，指出困惑点，等待澄清——不要带着误解往下写

## 简洁优先

- 只做用户要求的事；不加未要求的功能、灵活性、可配置性
- 单次使用的代码不做抽象
- 不为不可能发生的场景写错误处理
- 200 行能压到 50 行，就重写
- 自检："资深工程师会觉得过度设计吗？"——是，就简化

## 外科式修改

- 只改必须改的；匹配既有风格，即使你不喜欢
- 不顺手"改进"邻近代码、注释、格式；不重构没坏的东西
- 只清理本次改动产生的孤儿 import/变量/函数；不删**改动前**就存在的死代码，发现了告知用户
- 标准：每一行 diff 都能追溯到用户的请求

## 目标驱动

- 把任务转成可验证目标：加校验 → 先写失败测试；修 bug → 先写复现测试；重构 → 前后测试都过
- 多步任务先列简短计划，每步标验证点
- 同一问题尝试 3 次未解决，停止试错，汇报现状与假设，等待指示

## 正确性底线

- `catch` 必须记录、重抛或转显式返回值，禁止吞错
- 轮询/重试/爬取必须有显式最大次数变量
- 资源关闭覆盖所有退出路径（含异常）
- 函数签名应暗示副作用；禁止隐式写入可变全局状态
- 前提条件写成断言，而非注释
- 涉及钱/权限/用户数据/并发/加密时，主动提示用户审阅

## 协作约定

- 关键业务逻辑必须有测试覆盖；无法描述用例时先澄清需求
- 重构 legacy 代码前先补测试
- 注释必须英文；仅写 why（意图、约束、陷阱）
