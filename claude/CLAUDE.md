# 开发指南

正确性 > 可读性 > 性能。行为不变优先于重构；代码风格服从项目 linter/formatter。

## 工作方式

- 动手前先澄清：假设必须显式说明；存在多种合理解读时，列出选项让用户选，不替用户拍板。
- 动手中遇到困惑就停下：说明卡点、可选方案和影响，等待确认，绝不带着误解继续。
- 发现更简单方案要指出；必要时推回过度设计或风险方案。
- 库、框架、SDK、API、CLI 不确定时，用 context7 或 exa 查最新文档，禁止凭记忆编造。
- 内部数据结构/字段名不确定时，先查 schema/代码定义，不凭经验或记忆假设命名。

## 修改原则

- 只做用户要求的事；不增加未要求的功能、抽象、配置或兼容层。
- 改前先搜现有实现，优先复用既有函数、工具、模式，而非新建平行实现。
- 引入新依赖前先确认：能用标准库或现有依赖解决就不加新包；必须新增时先告知用户及理由。
- 只改必须改的代码；匹配既有风格，不顺手重构、格式化或“改进”邻近代码。
- 单次使用的逻辑不抽象。
- 只处理已知可达的失败路径。
- 每一行 diff 都必须能追溯到用户请求；只清理本次改动产生的孤儿 import、变量、函数。
- 发现改动前已存在的死代码或问题，只告知用户，不擅自删除。

## 验证标准

- 把任务转成可验证目标：加校验 → 先写失败测试；修 bug → 先写复现测试；重构 → 前后测试都过。
- 关键业务逻辑必须有测试覆盖；无法描述用例时先澄清需求。
- 项目暂无测试框架不等于跳过验证：逐步引入测试，优先覆盖本次改动的关键路径。
- 重构 legacy 代码前先补测试。
- 多步任务先列简短计划，并标明每步验证点。
- 同一问题尝试 3 次未解决，停止试错，汇报现状、证据和假设，等待指示。
- 非代码任务（报告、配置、数据文档）同理：动手前先核对权威数据源（数据库/API/CLI 实时结果），不凭记忆或旧记录推算；产出后与相关文件交叉核对一致性。

## 正确性底线

- `catch` 必须记录、重抛或转显式返回值，禁止吞错。
- 轮询、重试、爬取必须有显式最大次数变量。
- 资源关闭必须覆盖所有退出路径，包括异常路径。
- 函数签名应暗示副作用；禁止隐式写入可变全局状态。
- 前提条件写成断言或显式校验，而不是注释。
- 涉及钱、权限、用户数据、并发、加密时，主动提示用户审阅。

## 注释

- 代码自解释优先：好命名、小函数胜过注释；注释解释 why（意图、权衡、为什么不那样写），不复述代码的 what。
- 必须注释的场景：关键业务逻辑、公共 API、并发、权限、金额、兼容性——用英文注释或文档注释写清 why、业务约束、边界条件和陷阱；公共 API 还需写明参数、返回、异常、前置/后置条件。
- 注释随代码同步更新或删除，过期注释比没有更危险；不写复述代码的废话、注释掉的死代码（交给 git）、变更日志（交给 commit）。

## 工具约定

- 单文件 Python 脚本一律用 `uv run <script>.py` 执行；依赖以 PEP 723 内联元数据声明在文件头部（`# /// script` ... `dependencies = [...]` ... `# ///`），不手动建 venv/requirements.txt。
- 多文件 Python 项目用 `uv`（`uv venv` / `uv add` / `uv sync`）统一管理依赖和虚拟环境，不手动 `pip install` 到全局或裸 venv。
- 文本/代码搜索优先用 `rg`（ripgrep）而非 `grep -r` 或 `find | grep`。
- 按文件名/路径搜索优先用 `fd` 而非 `find -name`/`-iname`。
