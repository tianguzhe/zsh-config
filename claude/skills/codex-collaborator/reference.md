# Codex Collaborator - 协作流程参考

## 四阶段协作流程详解

### 流程图

```
用户需求
   ↓
┌──────────────────────────────────────────┐
│ 阶段 A：需求分析                         │
│ - Claude 分析用户需求                    │
│ - 调用 Codex 完善需求和计划              │
│ - 批判性质询（至少1个问题）              │
│ - 记录 SESSION_ID 和确认的需求           │
└──────────────┬───────────────────────────┘
               ↓
┌──────────────────────────────────────────┐
│ 阶段 B：原型获取                         │
│ - 调用 Codex 获取 unified diff 原型      │
│ - 验证格式和安全性                       │
│ - 批判性质询设计决策                     │
│ - 归档原型作为实现基线                   │
└──────────────┬───────────────────────────┘
               ↓
┌──────────────────────────────────────────┐
│ 阶段 C：代码实现                         │
│ - 基于原型重写生产级代码                 │
│ - 记录与原型的差异                       │
│ - 运行测试并记录结果                     │
│ - 准备审查材料                           │
└──────────────┬───────────────────────────┘
               ↓
┌──────────────────────────────────────────┐
│ 阶段 D：审查复盘                         │
│ - 调用 Codex 审查代码和需求完成度        │
│ - 批判性验证审查结论                     │
│ - 决定通过或返回修复                     │
│ - 记录经验教训                           │
└──────────────┬───────────────────────────┘
               ↓
           完成/返回修复
```

## SESSION_ID 管理指南

### SESSION_ID 的生命周期

1. **生成**
   - 时机：首次调用 `mcp__codex__codex` 工具时
   - 方式：工具自动生成 UUID 并返回
   - 格式：标准 UUID（如 `019aabca-a9f3-7783-8343-3deca9526275`）

2. **传递**
   - 在每次调用 `mcp__codex__codex` 时传递同一个 SESSION_ID
   - 确保同一个任务的所有阶段使用相同的 SESSION_ID
   - 在 TodoWrite 中记录当前 SESSION_ID

3. **存储**
   ```markdown
   ## 当前协作会话
   - SESSION_ID: 019aabca-a9f3-7783-8343-3deca9526275
   - 阶段: B (原型获取)
   - 开始时间: 2024-02-04 10:30
   ```

4. **关闭**
   - 阶段 D 完成并通过审查后
   - 任务被取消或中断时
   - 记录关闭原因和最终状态

### SESSION_ID 记录模板

```yaml
session_id: 019aabca-a9f3-7783-8343-3deca9526275
task: "实现 Android 分享功能"
phases:
  - phase: A
    status: completed
    summary: "需求已确认，包含在线/离线分享场景"
    codex_insights: "建议添加缓存策略"
    challenges: "离线模式的数据持久化方案"
  - phase: B
    status: completed
    summary: "原型已获批，包含 ViewModel、Repository、UI"
    codex_insights: "使用 WorkManager 处理后台分享"
    challenges: "是否需要额外的错误重试机制"
  - phase: C
    status: in_progress
    summary: "实现中，已完成 ViewModel 和 Repository"
  - phase: D
    status: pending
```

## 批判性质询指南

### 为什么需要批判性质询？

根据用户的核心指令：
> "codex只能给出参考，你必须有自己的思考，甚至需要对codex的回答提出置疑。尽信书则不如无书，你与codex的最终使命都是达成统一、全面、精准的意见，所以你们必须不断争辩已找到通向真理的唯一途径。"

批判性质询不是形式主义，而是：
- 发现 Codex 可能遗漏的场景
- 验证建议的可行性和适用性
- 深化对问题的理解
- 确保最终方案的质量

### 各阶段的质询重点

#### 阶段 A - 需求分析

**质询方向**：
- **完整性**：是否遗漏了边界场景或用户故事？
- **可行性**：技术方案是否在当前架构下可行？
- **风险识别**：是否识别了所有潜在风险？
- **依赖关系**：是否考虑了所有外部依赖？

**示例质询**：
```
Q: "你提到的实施计划中，是否考虑了与现有权限系统的集成？"
Q: "如果第三方分享 SDK 不可用，是否有降级方案？"
Q: "这个需求是否会影响现有的数据流架构？"
Q: "是否需要考虑国际化和本地化？"
```

#### 阶段 B - 原型获取

**质询方向**：
- **设计完整性**：是否包含所有必要的组件？
- **测试覆盖**：原型中是否考虑了测试用例？
- **配置管理**：是否包含必要的配置文件？
- **安全性**：设计中是否存在安全漏洞？

**示例质询**：
```
Q: "这个 unified diff 是否包含了依赖注入的配置更新？"
Q: "原型中的错误处理是否覆盖了所有异常场景？"
Q: "是否需要数据库迁移脚本？"
Q: "UI 组件是否考虑了无障碍支持（Accessibility）？"
Q: "是否需要添加性能监控埋点？"
```

#### 阶段 C - 代码实现

**质询方向**（持续进行）：
- **偏差合理性**：与原型的差异是否有充分理由？
- **代码质量**：是否达到生产级标准？
- **测试充分性**：测试是否覆盖了关键路径？
- **性能影响**：是否引入性能瓶颈？

**示例质询**：
```
Q: "我将缓存从内存改为磁盘，这是否会影响分享响应速度？"
Q: "这个实现是否需要额外的单元测试？"
Q: "错误日志的级别是否合适？"
```

#### 阶段 D - 审查复盘

**质询方向**：
- **审查深度**：Codex 的审查是否足够深入？
- **建议可行性**：改进建议是否实际可行？
- **遗漏检查**：是否有 Codex 未发现的问题？
- **风险评估**：残留风险是否可接受？

**示例质询**：
```
Q: "你指出的并发问题在什么场景下会发生？"
Q: "你建议的改进是否会引入新的复杂度？"
Q: "是否还有其他潜在的内存泄漏风险？"
Q: "测试覆盖率是否足够？如果不够，应该补充哪些测试？"
```

### 质询技巧

1. **具体而非抽象**
   - ❌ "这个设计有问题吗？"
   - ✅ "这个设计在用户网络切换时会如何表现？"

2. **挑战假设**
   - ❌ 接受 "这样就够了"
   - ✅ "你说这样就够了，但是否考虑了 [具体场景]？"

3. **追问细节**
   - ❌ 接受模糊回答
   - ✅ "你提到了性能问题，能具体说明在什么数据量级下会出现？"

4. **反向思考**
   - ❌ 只问正面场景
   - ✅ "如果这个功能失败了，会对系统的其他部分造成什么影响？"

## 只读安全保障机制

### 为什么强制只读模式？

1. **安全性**：防止 Codex 意外修改或删除代码
2. **可控性**：所有代码改动必须由 Claude 主动执行
3. **可追溯性**：通过 unified diff 清晰了解改动内容
4. **审查质量**：强制进行人工审查而非自动应用

### 只读模式的实施

#### 调用 Codex 时的标准配置

```python
mcp__codex__codex(
    PROMPT="[你的提示词]",
    cd="/Users/yikwing/AndroidStudioProjects/ykmagic",
    SESSION_ID="[UUID]",
    sandbox="read-only",  # 强制只读
    skip_git_repo_check=True
)
```

#### PROMPT 中的安全声明

在每个阶段的 PROMPT 中，都应该包含：

**阶段 B 的安全声明**（最关键）：
```
## 安全约束
- **仅输出 unified diff patch 格式**
- **不要实际创建或修改文件**
- **不要执行任何写入命令（如 touch, echo >, cat <<EOF）**
- **不要生成可执行脚本**

你当前处于 sandbox="read-only" 模式，只能提供建议和 diff，不能进行任何写操作。
```

**其他阶段的安全提醒**：
```
注意：你只需要给出分析和建议，不要进行任何代码修改。
```

### 输出验证清单

收到 Codex 的回复后，检查：

- [ ] **格式验证**：阶段 B 的输出是否为标准 unified diff 格式？
- [ ] **命令检查**：是否包含写入命令？
  - `rm`, `mv`, `cp`
  - `touch`, `mkdir`
  - `echo >`, `cat >`, `tee`
  - `sed -i`, `awk` with file modification
  - `git apply`, `patch`
- [ ] **脚本检查**：是否包含可执行脚本文件？
- [ ] **行为描述**：是否只提供了分析和建议？

### 违规处理

如果发现 Codex 的输出包含写入操作：

1. **立即指出问题**
   ```
   ⚠️ 检测到违反只读约束：
   你的输出包含了 [具体的写入命令/操作]。

   请修正为：
   - 阶段 A/C/D：仅提供分析和建议
   - 阶段 B：仅提供 unified diff patch
   ```

2. **要求重新生成**
   - 使用同一个 SESSION_ID 继续对话
   - 明确指出需要修正的部分
   - 重新强调只读约束

3. **记录违规情况**
   - 在 TodoWrite 中记录此次违规
   - 分析为什么会出现违规（PROMPT 不够明确？）
   - 改进后续的 PROMPT 模板

## 常见问题解答

### Q1: 什么时候应该返回上一阶段？

**返回阶段 B 的情况**（在阶段 C 中）：
- 原型遗漏了必要的文件或配置
- 发现原型的设计有根本性问题
- 需求发生变化，需要更新原型

**返回阶段 C 的情况**（在阶段 D 中）：
- 审查发现严重的功能缺陷
- 测试覆盖不足
- 代码质量未达到生产标准

### Q2: 如果 Codex 的建议与项目现有架构冲突怎么办？

1. **明确指出冲突**
   ```
   你建议使用 [方案 A]，但项目当前使用的是 [方案 B]。
   切换到 [方案 A] 会导致 [具体影响]。
   ```

2. **提供上下文**
   - 在下一次 PROMPT 中补充项目架构信息
   - 引用具体的代码文件或文档

3. **请求替代方案**
   ```
   考虑到现有架构，是否有在 [方案 B] 框架下的替代实现？
   ```

### Q3: SESSION_ID 丢失或混淆了怎么办？

**预防措施**：
- 每个阶段开始时在 TodoWrite 中记录 SESSION_ID
- 使用明确的命名（如在注释中记录）

**补救措施**：
- 查看之前的工具调用记录
- 如果无法恢复，开始新的 SESSION（但要记录原因）

### Q4: 是否可以并行运行多个协作流程？

**可以，但需要注意**：
- 每个流程使用不同的 SESSION_ID
- 在 TodoWrite 中明确区分不同的任务
- 避免在同一个文件上并行修改

### Q5: 如果阶段 D 审查发现大量问题，是否应该放弃当前实现？

**评估标准**：
- 问题的严重程度（功能性 vs 优化性）
- 修复成本 vs 重做成本
- 当前实现是否偏离了原型基线

**决策建议**：
- 功能性缺陷：返回阶段 C 修复
- 设计方向错误：返回阶段 B 重新设计
- 需求理解错误：返回阶段 A 重新分析

## 最佳实践

### 1. 明确的阶段边界

- 每个阶段完成时，在 TodoWrite 中明确标记
- 记录阶段产出和关键决策
- 不要跨阶段混合操作

### 2. 充分的文档记录

**应该记录的内容**：
- SESSION_ID 和任务描述
- 每个阶段的 Codex 回复摘要
- 所有批判性质询和回答
- 与原型的偏差及原因
- 审查结论和改进建议

**记录位置**：
- TodoWrite：进度跟踪
- 代码注释：重要设计决策
- Commit message：最终实现的总结

### 3. 高质量的 PROMPT

**PROMPT 应该包含**：
- 明确的任务描述
- 必要的上下文信息
- 具体的输出要求
- 安全约束声明

**PROMPT 的结构**：
```markdown
## 背景
[提供足够的上下文]

## 任务
[明确要 Codex 做什么]

## 要求
[具体的格式、约束、输出要求]

## 安全约束
[只读模式、禁止写入等]
```

### 4. 渐进式改进

- 不要期望一次就得到完美的结果
- 通过质询和迭代逐步完善
- 记录经验教训，改进后续流程

### 5. 保持务实

- 避免过度形式化
- 根据任务复杂度调整流程严格程度
- 简单任务可以合并某些步骤（但要记录）

## 流程优化建议

### 适用场景判断

**适合使用完整四阶段流程**：
- 新功能模块开发
- 重大重构
- 复杂的业务逻辑实现
- 需要多文件协同修改的任务

**可以简化流程**：
- Bug 修复（可能只需要阶段 D）
- 简单的代码调整
- 配置文件修改
- 文档更新

### 时间管理

**各阶段的典型时间分配**（参考）：
- 阶段 A：10-15%（需求理解和验证）
- 阶段 B：20-25%（原型设计和审查）
- 阶段 C：50-60%（代码实现和测试）
- 阶段 D：10-15%（审查和复盘）

**如果某个阶段耗时过长**：
- 检查是否遗漏了关键信息
- 评估是否需要拆分任务
- 考虑是否需要额外的技术调研
