# Codex Collaborator - 详细流程参考

## 四阶段协作流程图

```
用户需求
   ↓
┌──────────────────────────────────────────┐
│ 阶段 A：需求分析                         │
│ 输入：用户需求、技术上下文               │
│ 动作：调用 Codex 完善需求，批判性质询    │
│ 输出：确认需求、风险清单、SESSION_ID     │
│ 回退：需求不成立 → 终止                  │
└──────────────┬───────────────────────────┘
               ↓
┌──────────────────────────────────────────┐
│ 阶段 B：原型获取                         │
│ 输入：确认需求、技术约束                 │
│ 动作：调用 Codex 获取 unified diff       │
│ 输出：批准的 diff 原型、设计说明         │
│ 回退：需求变更 → 回 A（最多1次）         │
└──────────────┬───────────────────────────┘
               ↓
┌──────────────────────────────────────────┐
│ 阶段 C：代码实现                         │
│ 输入：批准原型                           │
│ 动作：手写生产级代码，记录偏差与测试     │
│ 输出：最终 diff、测试结果、偏差说明      │
│ 回退：原型不足 → 回 B（最多1次）         │
└──────────────┬───────────────────────────┘
               ↓
┌──────────────────────────────────────────┐
│ 阶段 D：审查复盘                         │
│ 输入：最终 diff、需求、测试结果          │
│ 动作：调用 Codex 审查，批判性验证        │
│ 输出：审查结论、残留风险、经验教训       │
│ 回退：功能缺陷 → 回 C（最多1次）         │
└──────────────┬───────────────────────────┘
               ↓
           完成/关闭 SESSION
```

## SESSION_ID 管理指南

### 生命周期

| 阶段 | 操作 |
|------|------|
| 生成 | 阶段 A 首次调用 `mcp__codex__codex` 时自动生成 UUID |
| 传递 | 后续每次调用传递同一 SESSION_ID |
| 记录 | 在 TodoWrite 中显式保存，格式：`SESSION_ID: 019aabca-...` |
| 关闭 | 阶段 D 完成或任务终止时 |

### 记录模板

```yaml
session_id: 019aabca-a9f3-7783-8343-3deca9526275
task: "实现分享功能"
current_phase: B
phases:
  A: completed - 需求已确认
  B: in_progress - 获取原型中
  C: pending
  D: pending
```

## 回退规则详解

### 回退触发条件

| 回退路径 | 触发条件 | 处理方式 |
|---------|---------|---------|
| D → C | 审查发现功能缺陷、测试不足 | 修复后重新提交审查 |
| C → B | 原型遗漏必要组件、设计有根本问题 | 请求更新原型 |
| B → A | 需求发生变化、发现新的约束 | 重新分析需求 |
| A → 终止 | 需求不成立、技术不可行 | 记录原因，关闭任务 |

### 回退限制

- **每个方向最多回退 1 次**
- 超出限制时必须：
  1. 启动复盘：分析为什么多次回退
  2. 拆分任务：将大任务分解为小任务
  3. 或终止：记录原因，重新评估

### 收敛策略

- 同一阶段质询超过 2 轮后需收敛决策
- 设置时间上限，避免无限迭代
- 记录每次回退的原因和改进点

## 批判性质询指南

### 核心原则

> "codex只能给出参考，你必须有自己的思考，甚至需要对codex的回答提出置疑。"

批判性质询不是形式主义，而是：
- 发现 Codex 可能遗漏的场景
- 验证建议的可行性和适用性
- 深化对问题的理解

### 各阶段质询重点

#### 阶段 A - 需求分析

| 维度 | 示例问题 |
|------|---------|
| 完整性 | 是否遗漏了边界场景或用户故事？ |
| 可行性 | 技术方案是否在当前架构下可行？ |
| 风险 | 是否识别了所有潜在风险？ |
| 依赖 | 是否考虑了所有外部依赖？ |

#### 阶段 B - 原型获取

| 维度 | 示例问题 |
|------|---------|
| 设计完整性 | 是否包含所有必要的组件？ |
| 配置管理 | 是否包含必要的配置文件？ |
| 测试覆盖 | 原型中是否考虑了测试用例？ |
| 安全性 | 设计中是否存在安全漏洞？ |

#### 阶段 C - 代码实现

| 维度 | 示例问题 |
|------|---------|
| 偏差合理性 | 与原型的差异是否有充分理由？ |
| 代码质量 | 是否达到生产级标准？ |
| 测试充分性 | 测试是否覆盖了关键路径？ |

#### 阶段 D - 审查复盘

| 维度 | 示例问题 |
|------|---------|
| 审查深度 | Codex 的审查是否足够深入？ |
| 建议可行性 | 改进建议是否实际可行？ |
| 遗漏检查 | 是否有 Codex 未发现的问题？ |

### 质询技巧

1. **具体而非抽象**
   - ❌ "这个设计有问题吗？"
   - ✅ "这个设计在用户网络切换时会如何表现？"

2. **挑战假设**
   - ❌ 接受 "这样就够了"
   - ✅ "你说这样就够了，但是否考虑了 [具体场景]？"

3. **追问细节**
   - ❌ 接受模糊回答
   - ✅ "你提到了性能问题，能具体说明在什么数据量级下会出现？"

4. **反向思考**
   - ❌ 只问正面场景
   - ✅ "如果这个功能失败了，会对系统的其他部分造成什么影响？"

## 只读安全保障

### 为什么强制只读？

1. **安全性**：防止 Codex 意外修改或删除代码
2. **可控性**：所有代码改动必须由 Claude 主动执行
3. **可追溯性**：通过 unified diff 清晰了解改动内容
4. **审查质量**：强制进行人工审查而非自动应用

### 调用配置

```python
mcp__codex__codex(
    PROMPT="[你的提示词]",
    cd="{{PROJECT_PATH}}",
    SESSION_ID="{{SESSION_ID}}",
    sandbox="read-only",  # 强制只读
    skip_git_repo_check=True
)
```

### 输出验证清单

收到 Codex 回复后，检查：

- [ ] **格式验证**：阶段 B 输出是否为标准 unified diff？
- [ ] **命令检查**：是否包含写入命令？
  - `rm`, `mv`, `cp`
  - `touch`, `mkdir`
  - `echo >`, `cat >`, `tee`
  - `sed -i`, `awk` with file modification
  - `git apply`, `patch`
- [ ] **脚本检查**：是否包含可执行脚本？
- [ ] **行为描述**：是否只提供了分析和建议？

### 违规处理

如果发现 Codex 输出包含写入操作：

1. **立即指出问题**
   ```
   ⚠️ 检测到违反只读约束：
   你的输出包含了 [具体的写入命令/操作]。

   请修正为：
   - 阶段 A/C/D：仅提供分析和建议
   - 阶段 B：仅提供 unified diff patch
   ```

2. **要求重新生成**（使用同一 SESSION_ID）

3. **记录违规情况**，改进后续 PROMPT

## 常见问题

### Q1: 什么时候应该返回上一阶段？

| 情况 | 建议 |
|------|------|
| 原型遗漏必要文件 | C → B |
| 原型设计有根本问题 | C → B |
| 需求发生变化（阶段 B） | B → A |
| 需求发生变化（阶段 C） | C → B → A（逐级回退） |
| 审查发现严重缺陷 | D → C |
| 测试覆盖不足 | D → C |

### Q2: Codex 建议与项目架构冲突怎么办？

1. 明确指出冲突点
2. 在下一次 PROMPT 中补充项目架构信息
3. 请求在现有架构下的替代方案

### Q3: SESSION_ID 丢失怎么办？

- **预防**：每个阶段在 TodoWrite 中记录
- **补救**：查看之前的工具调用记录
- **最后手段**：开始新 SESSION，记录原因

### Q4: 是否可以并行多个协作流程？

可以，但需要：
- 每个流程使用不同的 SESSION_ID
- 在 TodoWrite 中明确区分
- 避免在同一文件上并行修改

## 流程优化建议

### 适用场景判断

| 场景 | 推荐流程 |
|------|---------|
| 新功能模块开发 | 全流程 A→B→C→D |
| 重大重构 | 全流程 A→B→C→D |
| 复杂业务逻辑 | 全流程 A→B→C→D |
| 需求明确的中等改动 | 简化 A→C→D |
| Bug 修复 | 仅 D 或 A→D |
| 配置文件修改 | 仅 D |
| 文档更新 | 直接执行 |

### 最佳实践

1. **明确的阶段边界**：每个阶段完成时在 TodoWrite 中标记
2. **充分的文档记录**：SESSION_ID、质询问答、偏差说明
3. **高质量的 PROMPT**：明确任务、提供上下文、声明约束
4. **渐进式改进**：通过质询和迭代逐步完善
5. **保持务实**：根据任务复杂度调整流程严格程度
