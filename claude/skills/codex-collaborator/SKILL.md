# Codex Collaborator Skill

## Purpose

此 Skill 标准化与 Codex MCP 的协作流程，确保在整个开发周期中：
- 需求分析充分且经过验证
- 代码原型以安全的 unified diff 形式提供
- 实现过程有明确的基线参考
- 代码审查全面且经过批判性思考

## Scope

此 Skill 涵盖：
- 与 Codex MCP 的四阶段协作流程
- SESSION_ID 的管理和传递
- 只读模式（sandbox="read-only"）的安全保障
- 每个阶段的批判性质询机制

不涵盖：
- 简单的单次代码生成（直接使用 Codex MCP 工具即可）
- 不需要多轮迭代的任务

## When to Use This Skill

**自动触发条件**：
- 用户明确要求使用 Codex 协作流程
- 任务涉及需求分析、原型设计、代码实现、代码审查的完整周期
- 需要与 Codex MCP 进行多轮对话的复杂功能实现

**手动考虑使用**：
- 实现新的业务功能或模块
- 重构现有代码时需要验证设计方案
- 需要详细的代码审查和质量保证

## How It Works

### 四阶段协作流程

```
┌─────────────────┐
│ A. 需求分析     │ → 与 Codex 完善需求和计划
└────────┬────────┘
         ↓
┌─────────────────┐
│ B. 原型获取     │ → 获取 unified diff 原型（只读模式）
└────────┬────────┘
         ↓
┌─────────────────┐
│ C. 代码实现     │ → 基于原型实施，记录偏差
└────────┬────────┘
         ↓
┌─────────────────┐
│ D. 审查复盘     │ → Codex 审查 + 批判性验证
└─────────────────┘
```

### SESSION_ID 管理

- **生成时机**：开始阶段 A 时，Codex MCP 工具会自动生成 UUID
- **传递方式**：在每次调用 Codex MCP 工具时传递同一个 SESSION_ID
- **生命周期**：从阶段 A 开始到阶段 D 完成
- **记录要求**：在每个阶段的 TodoWrite 中记录当前 SESSION_ID

## Instructions

### 阶段 A：需求分析

**目标**：与 Codex 共同完善需求分析和实施计划

**步骤**：
1. **理解用户需求**
   - 分析用户的初始需求
   - 识别技术约束和业务目标
   - 确定交付物和验收标准

2. **调用 Codex 完善需求**（使用 mcp__codex__codex 工具）
   ```
   PROMPT:
   ## 需求分析
   [你对需求的理解]

   ## 初步思路
   [你的初步实现思路]

   ## 请求
   请帮我：
   1. 完善需求分析，指出遗漏的场景和边界条件
   2. 优化实施计划，建议具体的实现步骤
   3. 识别潜在风险和依赖
   4. 提醒我应该质疑的关键点

   注意：你只需要给出分析和建议，不要进行任何代码修改。

   cd: [项目根目录]
   sandbox: "read-only"
   ```

3. **记录 SESSION_ID**（重要！）
   - Codex 工具返回的结果中包含 SESSION_ID（UUID 格式）
   - **立即记录此 SESSION_ID**，后续所有阶段都需要使用
   - 在 TodoWrite 中创建一个专门的 todo 记录 SESSION_ID
   - 示例：`记录 SESSION_ID: 019aabca-a9f3-7783-8343-3deca9526275`

4. **批判性质询**（至少提出一个质疑）
   - "这个分析是否遗漏了边界场景？"
   - "实施计划的回滚策略是什么？"
   - "依赖关系是否完整？"
   - 记录 Codex 的回答

5. **确认并记录**
   - 在 TodoWrite 中记录确认的需求列表
   - 确保 SESSION_ID 已保存
   - 进入阶段 B

---

### 阶段 B：原型获取（只读 Diff）

**目标**：在不修改代码的情况下获取 unified diff 原型

**步骤**：
1. **调用 Codex 获取原型**（使用 mcp__codex__codex 工具）
   ```
   PROMPT:
   ## 任务
   基于阶段 A 的需求分析，请生成代码实现原型。

   ## 要求
   - **仅输出 unified diff patch 格式**
   - **不要实际创建或修改文件**
   - 为每个关键设计决策提供说明
   - 指出需要补充的测试用例

   请生成 unified diff patch。

   cd: [项目根目录]
   SESSION_ID: [上一阶段的 SESSION_ID]
   sandbox: "read-only"
   ```

2. **验证原型格式**
   - 确认输出是标准的 unified diff 格式
   - 确认没有包含写入命令或脚本
   - 如果不符合要求，拒收并要求 Codex 修正

3. **批判性质询**（至少提出一个质疑）
   - "这个原型是否覆盖了所有需求？"
   - "是否遗漏了配置文件或测试用例？"
   - "设计中是否存在潜在的性能或安全风险？"
   - 记录 Codex 的回答

4. **确认并归档**
   - 将原型 diff 和设计说明保存
   - 在 TodoWrite 中标记原型已获批
   - 进入阶段 C

---

### 阶段 C：代码实现

**目标**：基于批准的原型实施代码，记录所有偏差

**步骤**：
1. **参考原型实现**
   - **仅将原型作为逻辑参考**
   - **重写为生产级代码**（高可读性、高可维护性）
   - 不要直接应用 diff，而是理解设计后手动实现

2. **记录实现过程**
   - 每个文件/模块的实现内容
   - 与原型的差异及原因
   - 测试情况和结果
   - 发现的新问题

3. **处理偏差**
   - 如果发现原型不足，返回阶段 B 请求更新
   - 记录所有偏离原型的改动和理由

4. **批判性质询**（持续进行）
   - "原型是否考虑了这个边界情况？"
   - "是否需要额外的错误处理？"
   - "测试覆盖是否充分？"

5. **准备审查材料**
   - 生成最终的代码 diff
   - 整理需求对照表
   - 收集测试结果
   - 进入阶段 D

---

### 阶段 D：审查复盘

**目标**：通过 Codex 审查代码，并进行批判性验证

**步骤**：
1. **调用 Codex 进行审查**（使用 mcp__codex__codex 工具）
   ```
   PROMPT:
   ## 审查请求
   请审查以下代码改动和需求完成情况。

   ## 审查材料
   - 最终代码 diff：[提供 diff 或文件路径]
   - 需求列表：[阶段 A 的需求]
   - 测试结果：[测试情况]

   ## 审查维度
   1. **功能正确性**：代码是否正确实现了所有需求？
   2. **需求覆盖**：是否有遗漏的需求或边界情况？
   3. **潜在风险**：是否存在安全、性能或可维护性问题？
   4. **测试充分性**：需要补充哪些测试用例？

   请提供详细的审查报告。

   cd: [项目根目录]
   SESSION_ID: [同一个 SESSION_ID]
   sandbox: "read-only"
   ```

2. **批判性验证**（必须进行）
   - 逐条质疑 Codex 的审查结论
   - "你指出的这个问题是否真的会发生？"
   - "你建议的改进是否考虑了现有架构？"
   - "是否遗漏了其他潜在风险？"
   - 记录所有质疑和回答

3. **最终决议**
   - 如果发现问题：返回阶段 C 修复，记录原因
   - 如果审查通过：
     * 在 TodoWrite 中记录审查结论
     * 记录残留风险和后续改进点
     * 关闭 SESSION_ID

4. **复盘总结**
   - 需求与交付是否一致？
   - Codex 的建议是否有价值？
   - 批判性质询是否充分？
   - 经验教训和改进点

## Safety & Critical Thinking Guidelines

### 只读安全保障

**所有调用 Codex 的请求必须**：
- 明确声明 `sandbox="read-only"`
- 在 PROMPT 中强调"不要实际修改文件"
- 阶段 B 必须只要求 unified diff 格式

**检查 Codex 输出**：
- 是否包含写入命令（rm, mv, cat >, 等）
- 是否包含可执行脚本
- 如有违规，立即指出并要求修正

### 批判性质询要求

**每个阶段必须**：
- 提出至少一个具体的质疑问题
- 不接受模糊或敷衍的回答
- 记录质疑和 Codex 的详细回应

**质询清单**（选择性使用）：
- **功能覆盖**：哪些场景或边界条件未被覆盖？
- **原型完整性**：是否遗漏了配置、迁移或测试文件？
- **安全性**：是否存在潜在的安全漏洞？
- **可回滚性**：如果部署失败，如何快速回退？
- **性能影响**：是否存在性能瓶颈或不必要的开销？
- **可维护性**：代码是否易于理解和后续修改？
